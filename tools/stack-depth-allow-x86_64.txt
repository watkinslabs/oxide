# Static call paths at or over the stack-depth ceiling when the gate landed
# (x86_64). Tolerated at or below the recorded budget ONLY — a new or deeper
# path FAILS. Each block states why that family is legitimately deep; the
# gate refuses an entry that is not under a reason block, and fails on an
# entry naming a path that is no longer in the kernel.
#
# Entries are DEMANGLED paths (B1632). They used to be mangled symbols, whose
# crate disambiguator changes with the features the crate was built with, so
# the same source tree passed or failed depending on which build the gate
# happened to read. An old mangled entry is still accepted and normalised.
#
# Burn this down. Regenerate with:
#   make stack-gate-baseline-x86
#
# EMPTY, and it stays that way. B1618 removed the whole network TX/RX/socket-
# control family; B1620 removed fork/clone and, with it, the syscall entry and
# dispatch roots. B2038 removed the last four — `_start`, `_start_rust`,
# `kernel_main` and `rootfs::init` — the boot family, which had been carrying a
# ~20 KB budget on a 16 KB stack and had drifted 472 B past even that.
#
# Nothing about that path was inherently deep. Boot runs in strict phases and
# no phase's locals outlive it, but the phases were written as one function
# each, so the compiler reserved early-boot, the kthread spawns, the mount
# graph, the keymap scan buffer and the userspace handoff in a single prologue
# and held them all live underneath the deepest chain in the kernel. Splitting
# them into their own frames (Linux `noinline_for_stack`) took `_start` from
# 20488 B to 11096 B without moving a single line of logic.
#
# So every x86_64 path the linker can see is now under 13000 B with the
# schedule() blocking tail already charged, and ANY entry added here is a
# regression to fix, not a budget to record.
