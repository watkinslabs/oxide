# Static call paths at or over the stack-depth ceiling when the gate landed
# (x86_64). Tolerated at or below the recorded budget ONLY — a new or deeper
# path FAILS. Each block states why that family is legitimately deep; the
# gate refuses an entry that is not under a reason block, and fails on an
# entry naming a path that is no longer in the kernel.
#
# Entries are DEMANGLED paths (B1632). They used to be mangled symbols, whose
# crate disambiguator changes with the features the crate was built with, so
# the same source tree passed or failed depending on which build the gate
# happened to read. An old mangled entry is still accepted and normalised.
#
# Burn this down. Regenerate with:
#   make stack-gate-baseline-x86
#
# B1618 removed the whole network TX/RX/socket-control family from this file.
# B1620 removed the fork/clone family and, with it, the syscall entry/dispatch
# roots — with the deepest syscall under the ceiling the roots are under it
# too. Only the boot path is left. Anything that trips the gate now is a
# regression, not a candidate for a new entry here.

# Boot path, and NOT on a task stack. `_start` -> `kernel_main` runs on the
# static boot stack before any `Task` exists, and `kstack::alloc` has not yet
# handed out a 16 KiB guard-paged stack. The depth is real but the budget is
# a different one; re-check this block if the boot stack is ever resized.
#
# F774 raised each of these by 192 B: adding the SCHED_DEADLINE class grew
# `Task` by its deadline entity and `RunqueueInner` by a third class tree, and
# the boot path builds one of each on this stack (the idle task and the
# runqueue). Split 96 B in `install_default_runqueue` + 96 B in the task
# construction below it; it is a struct-size consequence of the class
# existing, not a new call chain.
#
# B1634 raised each of these by 16 B, x86_64 only (aarch64 absorbed it without
# moving). Namespace-aware quota ids require the superblock to record the user
# namespace it was mounted from, which grew `SuperBlock` 584 -> 592 B; the boot
# path tears a superblock down on this stack, so the extra 8 B lands in the
# teardown frames and rounds to 16 B after alignment. Struct-size consequence
# of the field existing, not a new call chain.
#
# The same lane also SHORTENED this family by 288 B before this 16 B: quota-off
# reached `dqput`, which upgraded the dquot's weak back-reference to its
# superblock, and the resulting temporary made superblock teardown appear to
# re-enter itself. A dquot does not own its superblock, so the teardown path
# now passes the borrowed one it already holds.
#
# B1638 raised each of these by 64 B. Measured, not estimated: `Task` grew
# 3624 -> 3656 B (+32) across the ptrace/prctl/arch_prctl/personality work, and
# the boot chain materialises a `Task` in TWO frames on the same path (the idle
# task's construction and the runqueue install above it), so a +32 struct shows
# up as +64 on each recorded root. This is the same shape as the F774 entry
# above, which split its +192 the same way.
#
# The +32 is eight new per-task fields, each one a value some syscall now
# CONSUMES rather than merely stores: `nocpuid` (ARCH_SET_CPUID), `shstk_features`
# and `shstk_locked` (the CET facility set and its lock), `tsc_sigsegv`
# (PR_SET_TSC's CR4.TSD trap), `tagged_addr` (arm64 PR_SET_TAGGED_ADDR_CTRL),
# `jobctl` (the group-stop / PTRACE_LISTEN latch), and the two `Lazy` handles for
# the x86 and arm64 hardware debug-register shadows. The debug-register shadows
# are deliberately behind `Lazy` — inline they would have been hundreds of bytes
# per task and would have pushed the aarch64 syscall path over its ceiling, which
# has no allowlist to absorb it.
#
# `ContextX86_64` also grew 0x40 -> 0x48 for the user `gs_base` the swapgs
# conversion introduced; it is embedded in `Task` and is part of the +32 above,
# not a separate charge.
