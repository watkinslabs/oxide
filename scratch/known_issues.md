# Known issues

Every row here is work this project WILL do. There is no not-going-to-fix status
and no deferral: a divergence from Linux is either fixed or it is an open row
waiting for its lane. A row that records a shape we chose on purpose still names
the work that makes it right, because "we meant to" is not a reason to leave
Linux behaviour unimplemented.

**This file is the only store of live work.** Any lane that finds an issue adds
its row HERE, to the section it belongs to, in the same PR that finds it. Any
lane that fixes one flips it to `FIXED <sha>` and MOVES it to
`scratch/fixed-issues.md` in the same PR. Rows are never deleted, only
relocated.

Per-lane drop files under `scratch/issues.d/` are abolished and the directory is
gone (C300 folded the last 77 rows back in). A row parked in a side file is a row
nobody reads: the fold step was skipped often enough that a third of the ledger
lived outside it, and six lanes each filed the same aarch64 stack-ceiling defect
without seeing the other five. A concurrent-lane conflict on this file is a
rebase round-trip and is worth it — resolve it by taking BOTH sides' rows, never
by dropping one.

Before filing, read the section your row belongs to. If a row already states the
fact, add your evidence to it rather than filing a second row: one fact, one row.

`Status`: `OPEN` | `IN-PROGRESS <branch>` | `FIXED <sha>`.

`Owner`: `NEXT` is the queue head. Those rows are claimed before any unowned
work and become `IN-PROGRESS <branch>` when the current integration finishes.

`Class` says what KIND of work the row needs, never whether it gets done:

| Class | Means |
|---|---|

`Sev`: `blocker` (merge gate) | `high` (wrong answer reaching userspace) |
`med` (missing surface) | `low` (hygiene, tooling, cosmetics).
