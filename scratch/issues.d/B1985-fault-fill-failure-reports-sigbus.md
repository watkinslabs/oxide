# B1985 — fault-fill failure reports the reference's signal

| Status | Class | Sev | Issue | Evidence | Owner |
|---|---|---|---|---|---|
| OPEN | MISSING | med | **There is no global out-of-memory killer, and the fault path's OOM leg now depends on one.** A fault that cannot obtain a frame reports the reference's out-of-memory outcome: no signal, resume userspace, re-take the instruction — on the contract that the memory-pressure path has already posted a fatal signal on its victim. That contract holds for a memcg charge failure (`mm-pmm/src/memcg.rs` `MemoryPressure::Max` reclaims, then `sched::oom::kill_memcg`), and does NOT hold for plain frame exhaustion: `alloc_one_frame` returning `None` kills nothing, so the instruction re-faults forever. The reference relies on its page allocator invoking the OOM killer before returning failure, which is why its own fault-side handler only warns and retries. Closing this means a global OOM selector on the allocator failure path, not a change to the fault classification. | `crates/kernel/mm-vmm/src/fault_signal.rs` `FaultFailure::Oom`; the only OOM selector in the tree is `sched::oom::kill_memcg`, reached solely from the cgroup pressure hook (grep: no other caller). Partly mitigated: `mm-pmm/src/user_as/signal.rs` prints `[FAULT-RESOLVE] out of memory; no signal, re-taking` once per boot, but only under `debug-faultdiag` — the klog policy (`04§4.0`, spec-lint `code/klog-ungated`) forbids an ungated production log, so a default build hangs silently. Previously this reason terminated the task with SIGSEGV, which is not what the reference reports. | unowned |
| OPEN | INFRA | med | **`make stack-gate` fails on `main` for aarch64, unrelated to any lane.** `oxide_svc_save_block` reaches 13120 B against the 13000 B ceiling on a 16384 B stack, through `oxide_syscall_dispatch` -> `sys_io_uring_enter` / `sys_io_submit` / `sys_sendmmsg`. Measured on this branch and again with every change on this branch fully reverted: identical 13120 B, same 9259 functions scanned. The main checkout's on-disk aarch64 ELF reports 12992 B (8 B of headroom) but scans only 8879 functions, so it is a stale artifact and not a baseline. Any lane touching aarch64 will now see this gate red and may misattribute it. | `python3 tools/stack-depth-gate.py target/aarch64-unknown-oxide-kernel/release/oxide-aarch64 --arch aarch64 --fail 13000` at `d605a3613` with a clean tree. x86_64 passes. | unowned |
