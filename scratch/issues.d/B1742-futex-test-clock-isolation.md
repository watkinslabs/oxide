| Status | Class | Sev | Issue | Evidence | Owner |

| FIXED (this PR) | COVERAGE | high | **`futex_core_hosted` drove one process-wide fake clock from three tests at once, and the production wait loop reads it — so a test could hang forever on another test's write.** `FAKE_NOW_NS` is a single `AtomicU64` consulted by `wait::wait_loop`'s `now_monotonic_ns() >= deadline_ns` check, and cargo runs the file's tests concurrently on separate threads. A sibling storing `501` between this test's waiter being woken and its own deadline recheck makes a 1000 ns deadline read as not-yet-elapsed, so the loop takes the reference's genuine "spurious wakeup, retry" path (`__futex_wait`) and re-parks with nothing left to wake it. The futex code was right throughout; the harness was the defect. A `fake_clock()` guard now serialises the three tests that drive it and resets the clock on acquire, so each starts from a known time rather than inheriting whatever ran last. The guard is held across the spawned waiter, because the loop reads the clock from there too. | Whole workspace: **13156 passed / 0 failed** — green for the first time. The file alone: 0 failures in 25 consecutive runs. The mechanism is tested deterministically rather than by luck (`the_fake_clock_guard_excludes_and_resets`): a second acquirer is shown blocked while the first holds it, the clock is shown unmodified meanwhile, and the reset is asserted on both acquires — a timing bug's fix cannot be proved by one green run. | B1742 |
