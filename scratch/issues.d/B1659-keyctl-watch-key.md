# B1659 — `KEYCTL_WATCH_KEY` / watch queues

| Status | Sev | Issue | Evidence | Owner |
|---|---|---|---|---|
| OPEN | high | **Not this lane's bug, blocks every lane:** `cargo test -p fs` does not build at `origin/main`. The IPv4-options lane (`d3836ac4f`, `bdd6559df`) left `ipv4_options`, `raw4`, `send_control` and `sock_v6_name` ungated in `net/src/lib.rs` while they use `sock_opts`, which is `cfg(any(target_os="oxide-kernel", test, feature="hosted"))`. Any hosted build of `net` *as a dependency* fails with 10 errors; the cascade reaches `ping/*` and `stack/ipv4.rs` too, so it is not a two-line gate. B1659 works around it with a `net = { features = ["hosted"] }` **dev-dependency** in `crates/kernel/fs/Cargo.toml`, marked TEMPORARY — delete that line when net's hosted build is whole. | Reproduce on clean `main`: `cargo test -p fs --lib --no-run`. | net/ip-options lane |
| OPEN | med | The watch queue holds each note as its own allocation instead of a preallocated note array, so `IOC_WATCH_QUEUE_SET_SIZE` reserves a COUNT rather than memory. The syscall-visible contract is identical (same depth, same rounding to a whole page of notes, same EBUSY on a second call, same loss behaviour when full), but a queue's memory is charged as it fills rather than up front, and the pipe-buffer accounting Linux applies (`account_pipe_buffers`, the unprivileged EPERM when a user is over the soft/hard buffer limits) has no equivalent here. A local unprivileged user can therefore hold more notification memory than Linux would allow. Fix with the pipe-buffer user accounting, which does not exist in this kernel yet for ordinary pipes either. | B1659, `watch_queue/queue.rs::set_size`. | — |
| OPEN | med | Notification records are delivered only for KEY events. Linux also posts `WATCH_TYPE_MOUNT_NOTIFY`/`WATCH_TYPE_SB_NOTIFY` from the mount and superblock code in trees that carry those patches, and the generic `watch_queue` device (`/dev/watch_queue`) is absent here too — a notification pipe is reachable only through `pipe2(O_NOTIFICATION_PIPE)`. The mechanism is general (types are a filterable field and the filter code accepts any type below `WATCH_TYPE__NR`); what is missing is other subsystems calling it. | B1659; `WATCH_TYPE_NR` is 2. | — |
| OPEN | low | A watch on a key whose notification pipe has been closed keeps posting into a queue nobody can read. The queue stays alive because the watch holds a reference to it, so nothing leaks and nothing is corrupted, but the watch is never torn down: Linux drops the queue's watches when the pipe is released (`watch_queue_clear`). The visible effect is a key carrying a dead watch entry until the key itself dies. Fix: have `detach` walk the queue's own watch list. That list is not kept today — a watch points at its queue, not the other way about. | B1659, `watch_queue/registry.rs::detach`. | — |
| OPEN | low | `security_watch_key` / `security_post_notification` have no LSM hook here, so watching is gated by `KEY_NEED_VIEW` alone and a record is never withheld from a watcher whose credentials an LSM would reject. Matches a kernel with no LSM stacked, which is what this one is. | B1659, `ops/watch.rs::watch_key_core`. | — |
