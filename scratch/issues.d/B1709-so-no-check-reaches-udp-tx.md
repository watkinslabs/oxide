# B1709 — SO_NO_CHECK reaches the IPv4 UDP transmit path

| Status | Sev | Issue | Evidence | Owner |
|---|---|---|---|---|
| FIXED B1709 | med | `SO_NO_CHECK` was admitted, stored and readable with zero consumers: the IPv4 UDP builder always computed a checksum, so the option could not change a single wire byte. The flag now reaches `UdpHdr::build_into_opts` through the socket-owned transmit path (v4 and the v4-mapped AF_INET6 path), and the segmentation planner is handed the real value instead of a hardcoded `false`, so a socket asking for both `UDP_SEGMENT` and a suppressed checksum is refused rather than emitting unchecksummed segments. Closes the `SO_NO_CHECK has zero consumers` half of the curated `IP_CHECKSUM inert` row. | `net::udp::tests::suppressed_checksum_leaves_the_field_zero_and_the_datagram_acceptable`, `net::udp::tests::a_computed_zero_checksum_is_transmitted_as_all_ones`, `net::tests_udp_no_check_tx` (3). Positive control: dropping the suppression branch in the builder turns 3 of them RED; restored, 1739/0. | — |
| OPEN (not a defect) | low | The `IP_CHECKSUM` half of that row is **correct as it stands**, not an unwired consumer. The reference emits the `IP_CHECKSUM` control message only for a datagram whose device handed up a whole-datagram checksum; every other case produces no message. Our receive metadata has three checksum states — none, partial, valid — and no "complete" state, because neither device class we run (loopback, virtio-net) ever reports one: the reference maps the virtio "data valid" bit to *unnecessary*, not *complete*. So a receive on our devices gives the same answer the reference gives on the same devices: no message. Wiring a producer would require inventing a checksum the device never computed. Re-open only if a device that reports a full receive checksum is added. | `netdev::packet_metadata::PacketChecksum` has no `Complete` variant; `net::cmsg` already emits the message when `RxMeta.checksum` is `Some`, and that consumer is test-covered. | — |
| OPEN | low | Two IPv4 TTL owners disagree, and the ledger row blaming the v4-mapped path has it backwards. `net::inet_tx::ipv4_ttl` resolves an unset `IP_TTL` to a flat 64, which **bypasses a route's hoplimit metric**; the v4-mapped UDP path instead passes 0, the sentinel `send_udp_pmtu_to_bound_opts_owner` resolves against `route.metrics.ipv4_hoplimit(64)` — which is the reference's order (socket value if set, else the route's hoplimit, else the default). So the curated `IP_TTL unset resolves to a wire TTL of 0` row describes a sentinel, not a wire value: no datagram has ever left with TTL 0 through that path. The real divergence is the opposite one, and it is in `ipv4_ttl`. Fixing it needs the u8 channel to carry "unset" distinctly from a legitimately set 0, which today it cannot. | `stack/ipv4.rs` `if ttl == 0 { route.metrics.ipv4_hoplimit(...) }`; `inet_tx::ipv4_ttl` returns `IPV4_DEFAULT_TTL` for the negative sentinel (db7a83151). `net::inet_tx::tests::the_ttl_a_datagram_carries_depends_on_whether_it_is_multicast` pins the current flat-64 answer. | — |
