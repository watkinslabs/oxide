# B1682 — fbcon had two serialization locks for one console

| Status | Sev | Issue | Evidence | Owner |
|---|---|---|---|---|
| FIXED B1682 | high | `fbcon` hosted tests serialized on TWO different statics — `kernel/tests.rs`'s `SERIAL` and `tests.rs`'s `KERNEL_TEST_LOCK` — while mutating ONE process-global console: `VT_STATE`, the registration `kernel_init`/`kernel_unregister` installs, the `FbconFlush` softirq slot and the preempt count. Two locks over one resource exclude nothing, so a `kernel/tests.rs` test and a crate-root `tests.rs` test ran concurrently and clobbered each other's flush probe, registration and pending bit. `kernel/tests.rs`'s own comment claimed it serialized "against the rest of the crate" — it could not. This was the single largest contributor to workspace-suite flake measured so far. | `cargo test -p fbcon` **4/30 clean before, 30/30 after**. Failing test varied run to run (`try_lock_vt_excludes_the_flush_softirq`, `one_line_of_output_damages_only_that_text_row`, `damage_coalesces_across_writes_between_flushes`), which is why per-package runs kept "passing". | — |
| OPEN | low | `answerback.rs` keeps a third module-private `SERIAL` for its own queue state. It did not appear in any observed failure and guards a different resource, so it is left alone — but the crate now has one lock that owns the console and one that owns the answerback queue, and nothing states which resource a new test must take. | Not observed failing. | — |
