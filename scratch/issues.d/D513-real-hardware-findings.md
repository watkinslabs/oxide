# D513-real-hardware-findings

Rows filed from a bare-metal-readiness audit (x86_64 desktop/workstation) plus
the runtime-performance probe that preceded it. Detail and per-system work
plans for the hardware rows: `scratch/real-hardware.md`.

| OPEN | MISSING | critical | **No framebuffer source on physical hardware.** The whole VT/fbcon/fbdev console stack is built and works, but `fbdev::init_scanout` has exactly one non-test caller — virtio-gpu. The multiboot2 header requests no framebuffer (type-5 tag absent), the info walk drops tag 8 (`_ => {}`), and `BootInfo` has no framebuffer fields. Bare metal therefore has no display output at all. Machinery-without-callers class. | `mb2.rs:52-68` (header tags), `mb2.rs:440-468` (tag walk), `boot-info/src/lib.rs:21` (struct), `drv-virtio-gpu/src/post_init/scanout.rs:171` (sole caller) | — |

| OPEN | MISSING | critical | **No USB host controller.** `modules/src/linux_usb/` is a module-registry shim (types/core/gadget, 945 lines) with no xHCI driver; grep for xHCI across `crates/` is empty. Only physical input driver is `drv-ps2-keyboard`, so a board without PS/2 has no keyboard. | `crates/kernel/modules/src/linux_usb/`, `crates/drivers/` listing | — |

A firmware framebuffer maps Strong UC, making console scroll visibly slow and a compositor non-viable. | `hal/src/lib.rs:119-120`, `hal-x86_64/src/vmm.rs:10-12`, grep `IA32_PAT` empty | — |

| OPEN | DEFECT | high | **Fixed per-syscall overhead ~2.06 µs, ~10x the reference.** 400k `read`/`write` on `/dev/zero` took 0.825 s on a clean release build under KVM. Warm `ls -R /usr` (98k entries, no I/O) spends 0.901 s of 1.106 s in kernel — ~9 µs/entry. The syscall exit tail runs unconditionally what the reference runs only behind a flag test: `fire_due_timers()` (global timer lock, POSIX slot walk, hardware deadline recompute + re-arm), `service_current_timers()` plus a second clock read, and ungated `record_syscall`/tracepoint fire. `exit_to_user_mode_loop` is correctly flag-gated. | `dispatch/core.rs:534-565`; guest probes on `7e9e57db3` | — |
| OPEN | DEFECT | high | **Every syscall from a non-leader thread takes the global task-registry lock.** `fire_due_timers()` → `timer_owner()` takes `REG.lock_irqsave()` whenever `tgid != tid`. Single-threaded processes skip it; threaded ones (systemd, dbus-broker, gdm, the desktop) pay it on every call, serialised on one lock. The tick path had this same lookup removed for exactly this cost — the syscall path was never given the same fix. | `sched/src/timers/clock.rs:33-37`, `sched/src/registry/tid.rs:37-45`, cost note at `sched/src/timers/runtime.rs:219-222` | — |
| OPEN | DEFECT | medium | **Syscall CPU time is billed to user, not system.** A 400k-syscall run reporting 0.825 s wall reports `user 0.821s / sys 0.000s`, so kernel-heavy workloads are invisible to any userspace profiler and to `time`. | guest probe: `dd if=/dev/zero of=/dev/null bs=1 count=200000` | — |
| OPEN | COVERAGE | medium | **`debug-syscost` is contaminated by unrelated tracing gated on the same feature.** `[UXWRITE]`/`[LSCAN]` diagnostics in the unix-socket path are `#[cfg(feature = "debug-syscost")]`, and each emits a busy-poll UART write, inflating the very per-syscall costs the profiler measures (~2-3x on `read`/`write` vs a clean build). Its poll/sendmsg figures cannot be trusted as filed. | `net/src/unix_sock/stream/send.rs:117-141`; clean-build vs syscost-build comparison of nr=0/nr=1 | — |
| OPEN | DEFECT | medium | **Console TX busy-polls the UART per byte in the writer's task.** `emit()` spins on LSR THRE then writes each byte; under KVM each byte is two exits, so a log line costs ~1-2 ms and the writing task blocks for all of it. The reference copies into a ring buffer and drains on the TX interrupt. TX is already off the IRQs-off path, so this is throughput, not latency-under-lock. | `crates/drivers/drv-uart-16550/src/lib.rs:140-151`; boot-log inter-line deltas of 3-4 ms/fragment | — |
| OPEN | MISSING | medium | **No fault-around on file-backed faults.** Each fault fills one page; the reference maps a batch around the faulting address, so exec and library startup take roughly an order of magnitude more faults than they need. | `crates/kernel/mm-vmm/src/address_space/fault/fill.rs` | — |
