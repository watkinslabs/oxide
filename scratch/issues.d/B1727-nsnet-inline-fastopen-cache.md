| FIXED (this PR) | DEFECT | high | **`tcp_fastopen::ClientCache` stored its `BUCKETS` lock array inline, making it 8192 B, which made `NsNet` 9336 B and gave `net::net_ns::state::materialize_state` a 9256 B stack frame — over half a 16 KiB kernel stack, reserved on entry whether or not the namespace state had to be created.** Every SYN delivered to a listener reaches it: `deliver_tcp_to_listener` → `tcp_fastopen::plan` → `enable_bits` + `ns_keys` → `materialize_state`, unconditionally, in softirq context. That put the worst interrupt-reachable path at 13872 B of 16384 before the trap frame, and a hardware IRQ provably nests into the softirq drain (`lapic/dispatch.rs` does `sti; do_softirq(); cli`), so the guard page was crossed by arithmetic, not by luck — which is what the ~50% intermittency of the serial `#DF` was. The reference does not inline this: its destination-metrics hash is a separately allocated bucket array the namespace refers to by pointer, and its fast-open context is a pointer in the namespace struct. The bucket array is now a heap allocation built by pushing one bucket at a time, so no array temporary is ever materialised on the stack. | Measured on clean release builds of `main` and this branch. `ClientCache` 8192 → 16 B; `NsNet` 9336 → ~1160 B; `materialize_state` frame **9256 → 1152 B**; worst interrupt-reachable path `rx_drain_softirq` **13872 → 10000 B**, `deliver_rx_in` 13024 → 9152 B — headroom 2512 → 6384 B. `frame-size-gate` x86_64 was **FAIL on main** (`9256 NEW`, ≥8192 ceiling) and now PASSes on both arches; `stack-depth-gate` x86_64 drops from 53 over-ceiling paths to 1. `cargo test -p net` 1947 passed / 0 failed. Guard: `the_bucket_array_is_not_stored_inline` fails if the array returns inline — positive control run, it reports `ClientCache is 8192 B — the bucket array is inline again`. | B1727 |

| OPEN | MISSING | med | **The per-CPU hardirq stack has no poison / high-water-mark instrumentation on either arch, and a guard hit on it is indistinguishable from one on a task stack.** The reference reports a stack's deepest touched byte (`CONFIG_DEBUG_STACK_USAGE`: poison at creation, scan for the high-water mark).
