# B1719 — per-superblock procfs identity

| Status | Class | Sev | Issue | Evidence | Owner |
|---|---|---|---|---|---|
| FIXED (this PR) | DEFECT | high | **`procfs::static_files::proc_root()` was a process-global cached `Arc`, so every `mount -t proc` in every namespace shared ONE root inode.** There was nowhere for a mount's own options to live, which is why `hidepid=`/`subset=` could not be expressed at all and `ProtectProc=`/`ProcSubset=` silently did nothing for every service that asked for them. The reference builds a fresh root inode per superblock in `proc_fill_super` and shares only the static `proc_dir_entry` skeleton (which `crate::reg` already is). Now: `ProcfsFs::new(info)` builds its own root per mount, the root carries `Arc<ProcFsInfo>`, and the same `Arc` is published in `sb.s_fs_info` where the reference keeps it. | `crates/kernel/procfs/src/fs_info.rs` (identity + decisions, ungated), `fs_impl.rs`, `static_files.rs::build_root`, `live/root.rs`. Guest proof on both arches, one `subset=pid` mount: x86 `sub_meminfo=0 sub_pids=59`, arm `sub_meminfo=0`, zero faults — against `sub_meminfo=1` before. | B1719 |
| FIXED (this PR) | MISSING | high | **`hidepid=` and `subset=` were undeclared and unimplemented**; the parameter table was `Some(&[])`, so `mount -t proc -o hidepid=2` returned EINVAL — honest, but the confinement was simply absent. Both are now declared and ENFORCED: `subset=pid` removes every non-process entry from lookup and readdir (Linux `proc_lookup`/`proc_readdir` `pidonly` gate), and `hidepid` gates pid directories at the reference's two thresholds — `HIDEPID_NO_ACCESS` on lookup, `HIDEPID_INVISIBLE` on readdir — through the same `has_pid_permissions` ladder, including the `gid=` group exemption and the absolute `ptraceable` mode. | `procfs::fs_info` 16 hosted tests incl. every accepted spelling, the rejected values (`3`, `5`, `OFF`, `0x2`), the threshold split (noaccess lists but does not open), the group exemption, and that `ptraceable` ignores it. Enforcement sites: `live/root.rs` (lookup + readdir), `live/pid_access.rs::pid_visible`. | B1719 |
| FIXED (this PR) | DEFECT | med | **A filesystem constructor's parameter slice is NOT its option source, and reading it silently dropped every option.** `mount(2)` carries options in the DATA BLOB; the slice holds only values that are pinned open files (`FSCONFIG_SET_FD`). The first cut of this lane read the slice, so every hosted test passed while the guest showed `meminfo` inside a `subset=pid` mount. The wiring decision now lives in `fs_info::info_for_mount(data, pinned)` — ungated, so it is testable — and `vfs::fs::split_monolithic` is the ONE splitter, extracted from `generic_parse_monolithic` rather than copied. | `a_mounts_options_come_from_the_blob_and_never_from_the_pinned_slice` fails against the shape that shipped. Guest before: `sub_meminfo=1`; after: `sub_meminfo=0`. | B1719 |
| FIXED 4905b1ebd | DEFECT | high | **A `#DF` (double fault) — kernel stack overflow — under a burst of serial-driven work.** Typing one compound command at the debug shell (`mkdir`; two `mount -t proc`; three `ls \| grep -c`; one deliberately-failing `mount -o hidepid=3`) double-faults the guest at t=7.73s: `vec=8 (#DF) rip=ffffffff8006d7af rsp=fffffb0000006000 rbx=00000000000003f8`. `rbx` is the COM1 base and `rsp` is on a stack guard page, so this is the guard-page catch of a stack overflow in the serial/klog path, not a procfs fault. NOT caused by this lane: the same kernel runs a plain `mount -t proc` + `ls` probe clean, and so does `origin/main`.
