# B1678 — fsconfig / mount_setattr probes

| Status | Sev | Issue | Evidence | Owner |
|---|---|---|---|---|
| NOT-A-DEFECT B1678 | med | Curated `## Desktop` row "`fsconfig(FSCONFIG_SET_FD)` returns EINVAL to systemd's `(sd-mkdcreds)` on an `anon_inode:[fscontext]` fd, and the following `mount_setattr` also returns EINVAL" is closed — **both calls are feature probes whose CORRECT answer is EINVAL**, and we give it. (1) The `fsconfig` call is the "has this filesystem been converted to the new mount API" probe: `FSCONFIG_SET_FD` with a deliberately nonexistent option name, no value, and the context's own descriptor as the auxiliary fd. EOPNOTSUPP would mean "unconverted", EINVAL means "converted, option unknown" — the answer the prober wants. (2) The `mount_setattr` call is the "is the new mount API present" probe, `mount_setattr(-EBADF, NULL, 0, NULL, 0)`; `usize = 0` is below the version-0 block size, which the reference rejects with EINVAL before the capability gate, and the prober reads any non-`ENOSYS`, non-success answer as "present". Our size ladder, ordering, no-op short circuit and attribute validation all match. | B1663 boot log: `[EINVAL nr=431 ... a1=5 a4=<same fd as a0> fdpath=anon_inode:[fscontext]]` from `(sd-mkdcreds)`, `(-userdbd)`, `(ostnamed)` and `systemd`, each immediately followed by `[EINVAL nr=442 a0=0xfffffff7 a1=0 a2=0 a3=0 a4=0]` (`0xfffffff7` = `-EBADF`). Probe call sites read in the guest's own systemd 259 sources (`mount_option_supported`, `mount_new_api_supported`). Pinned by `syscalls::fsconfig_abi::tests::the_converted_filesystem_probe_clears_admission_and_is_not_eopnotsupp` and `syscalls::mount_attr_abi::tests` (8 tests). | — |
| OPEN | high | **Unknown filesystem parameters are silently ACCEPTED, so the option-support query the probe above guards always answers "yes".** After the `SET_FD` probe succeeds, the prober asks `fsconfig(fd, FSCONFIG_SET_FLAG/SET_STRING, key, ...)` and reads success as "this filesystem supports this option". Every `fsopen`ed context here uses one generic parameter path that pushes ANY flag/string key into the classic mount-option string and returns Consumed; no filesystem declares a parameter set, so no unknown key is ever rejected. The reference's converted filesystems reject an unknown parameter with EINVAL, which is exactly the signal being read. Consequences observed in the desktop image: `ProtectProc=`/`ProcSubset=` are enabled for services because `proc` claims `hidepid` and `subset` — our procfs ignores its mount data entirely, so those confinements silently do nothing; cgroup2 delegation/`memory_recursiveprot` options and tmpfs/ext4 `usrquota` are claimed the same way. Security-relevant: a confinement userspace believes it applied is absent. | Generic path: the only parameter-ops implementation is the classic-mount one, whose flag/string arm stores the key unconditionally; the fs types are registered with option parsers that ignore unrecognised data (`proc`, `sysfs`, `cgroup2`, `devpts`, and the rest ignore mount data outright). Not fixed here: making the parameter set authoritative changes which mounts succeed, and this lane has no boot access to verify a rootfs/tmpfs mount does not start failing. Needs a lane that can boot both arches. | — |
| OPEN | low | `FSCONFIG_SET_FD` cannot succeed for ANY filesystem here — no fs declares an fd-typed parameter, and the generic parameter path rejects a file-valued parameter outright. Harmless for the probe above (which wants the rejection) but it means the fd-passing half of the new mount API is unimplemented. | Same trace; `FsValue::File` has no accepting consumer anywhere in the tree. | — |
