| IN-PROGRESS B1686 | high | **Unknown filesystem parameters are silently ACCEPTED.** `ClassicMountFsContextOps::parse_param` stores any flag/string key and returns Consumed, and no filesystem declares a parameter set, so no key is ever rejected on the `fsconfig` path. The reference rejects a key outside the filesystem's parameter table with EINVAL ("Unknown parameter"). | `crates/kernel/vfs/src/fs/fs_context/ops.rs:23-33`. Foundation landed on this branch: `vfs::fs::fs_parser` (spec types + the reference's `fs_lookup_key` semantics — flag/value agreement, `no<name>` negation gated on opt-in, unknown key kept distinct from wrong value shape), 7 ungated tests. | B1686 |
| OPEN | high | **`mount(2)` never builds an `FsContext`, so a fix confined to the parameter path would not fix real mounts.** `dispatch_mount` calls `ty.construct_with_flags(source, target, data, sb_flags)` — the raw comma-separated data string goes straight to the filesystem constructor, bypassing `vfs_parse_fs_param` entirely. libmount/systemd use `mount(2)` for real mounts and `fsconfig` only for probes, so rejecting unknown keys only on the context path would make the PROBE truthful while every real mount kept ignoring options. The reference funnels both through one verdict. This is where the blast radius lives: `ext4 -o data=ordered,errors=remount-ro`, `tmpfs -o noswap,huge=`, `devpts -o gid=5,mode=620,ptmxmode=000`, `proc -o hidepid=2`, `cgroup2 -o nsdelegate` all succeed today and would start failing against an incomplete table. | `crates/kernel/syscalls/src/fsmount_common/mount_dispatch.rs:84`; `crates/kernel/vfs/src/fs/api.rs:126-145`. | B1686 |
| OPEN | high | **`hidepid=` / `subset=pid` are NOT a parameter-table problem — procfs cannot express them at all.** Of the 22 registered filesystem types only 5 (`tmpfs`, `ramfs`, `ext4`, `autofs`, `fuse`) even receive the mount data string; the other 17, `proc` included, take `_` and discard it. And `procfs::static_files::proc_root()` returns a **process-global cached `Arc`**, so every `mount -t proc` in every namespace shares ONE root inode, leaving nowhere for per-mount option state. Per-mount `hidepid=` needs per-superblock root inodes first. **Consequence for the security framing: listing `hidepid` in a parameter table would NOT make `ProtectProc=` work — only implementing it does. Conversely a table that OMITS `hidepid` makes the support probe answer "no", and systemd then correctly stops claiming a confinement it is not getting.** Omission is the cheap honest fix; implementation is the real one. | `crates/kernel/syscalls/src/fsmount_common/registry.rs:118` (proc ctor discards data); `crates/kernel/procfs/src/static_files.rs:73-76` (cached singleton root). | B1686 |
| OPEN | med | A listed-but-ignored parameter is still a false claim of support: any key a table lists that the filesystem does not honour keeps the option-support probe lying about that key. Applies to every option of the 17 filesystems that discard their data string. Each needs an implementation or omission from the table — the choice cannot be made silently. | Same registry listing. | — |
