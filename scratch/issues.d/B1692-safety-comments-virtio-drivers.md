# B1692 — SAFETY comment audit, virtio + display + storage drivers

Audit of every `code/safety-missing` / `code/safety-short` finding in
`crates/drivers/{virtio,drv-virtio-*,drm,fbdev,fbcon,drv-nvme,drv-ahci}`.
Each block was read and its invariant established before a comment was written;
blocks that turned out unsound are rows below, not comments.

| Status | Sev | Issue | Evidence | Owner |
|---|---|---|---|---|
| FIXED B1692 | HIGH | `program_queue` used the DEVICE-supplied `queue_size` unchecked while allocating exactly ONE frame per ring area. A device advertising more descriptors than a frame holds (QEMU accepts `queue-size=1024` on virtio-blk) makes every driver's own descriptor/avail/used store run off the end of that frame — a kernel heap wild write whose value comes from the ring index. Now renegotiated down per Virtio 1.2 §4.1.4.3 and the queue refused if the device does not accept. | `virtio::queue_cfg::tests::oversized_device_queue_size_is_negotiated_down_to_one_frame`; positive control: with the clamp disabled the test FAILS (`ring.size` 1024 vs 256), with it enabled it passes | B1692 |
| FIXED B1692 | HIGH | virtio-gpu `uninstall_scanout` discarded `virtio::reset_device`'s `#[must_use]` confirmation (`let _ = ...`) and freed the command frame AND the multi-megabyte framebuffer regardless. The doc on `reset_device` says in as many words that an unconfirmed reset means freeing is unsafe. On an unconfirmed reset this returned a physical address the device still lists as resource backing to the buddy allocator. | `post_init::release::tests::an_unconfirmed_reset_releases_nothing_so_the_device_keeps_its_frames`; positive control: with the reset gate removed from `releasable_dma` that test FAILS, with it present it passes | B1692 |
| FIXED B1692 | HIGH | virtio-gpu `uninstall_scanout_after_failed_probe` freed both frames with NO device reset at all. It runs after `setup_scanout` completed ATTACH_BACKING (probe.rs already documents that the device's resource table then holds the framebuffer PA and that no DETACH is ever sent), so the freed run was device-referenced by construction. Now resets first and honours the confirmation. | Same `release` tests; both unwind paths funnel through `release_scanout_dma` | B1692 |
| FIXED B1692 | MED | virtio-gpu probe freed the command frame after a CTRLQ poll TIMEOUT — i.e. exactly when the descriptor is still device-owned and the device may still write the reply into it. Both the display-info poll and the EDID fetch now leak the frame and fail the probe instead; `edid::fetch` grew a `timed_out` out-param so a timeout is distinguishable from the legitimate "device declined EDID" case, which it previously was not. | `probe.rs` `retired`/`edid_timed_out` paths; `[VGPU] ... leaking command frame` klog | B1692 |
| OPEN | LOW | virtio-gpu runtime `submit_ctrl_for_key` / `present_rect_for_key` treat a submit timeout as a plain `false` and go on to reuse the SAME persistent ctx command frame for the next command while the device may still own the previous descriptor. Not memory-unsafe (the ctx frame is never freed on these paths, and teardown now gates on a confirmed reset) but a device that stalls once can have its late reply read as the next command's status. | `runtime.rs::submit_ctrl_for_key` returns `false` without poisoning the ctx | unowned |
