# B1723 — the `#DF` root-caused: device IRQs have no stack of their own

| Status | Class | Sev | Issue | Evidence | Owner |
|---|---|---|---|---|---|
| OPEN (root-caused, fix designed) | DEFECT | high | **Every device interrupt runs on the stack it interrupted, so a deep kernel stack plus one interrupt overflows into the guard page and double-faults.** Device vectors are installed with `ist = 0` — `idt.rs`'s own test asserts it (`idt[0x40].ist == 0`, "a regular IRQ vector is untouched") — so the CPU does not switch stacks and the handler's prologue consumes whatever is left of the current 16 KiB stack. Linux does the opposite and for exactly this reason: `arch/x86/kernel/irq_64.c` / `asm/irq_stack.h` run every device and system-vector handler on the per-CPU `hardirq_stack_ptr` via `call_on_irqstack`. **The fix is that: a per-CPU hardirq stack.** Note the constraint before implementing — Linux switches in SOFTWARE (`run_irq_on_irqstack_cond` skips the switch when already on the IRQ stack), which is re-entrancy-safe; routing device vectors to an IST slot instead is only safe while device IRQs cannot nest, and this kernel now deliberately runs with IRQs ON in places (the block-wait change), so a nested IRQ would clobber the outer IST frame. Implement the conditional software switch, not an IST index. | Faulting address resolved against the build's own ELF: `rip=ffffffff8006f04f` → **`drv_uart_16550::imp::rx_isr_msi`**, `rcx=ffffffff8006eb60` → `drv_serial::deliver` — i.e. the fault is INSIDE the UART RX interrupt handler. `rsp=0xfffffb0000006000` is EXACTLY `slot_stack_lo` (`KSTACK_VA_BASE + slot*0x5000 + PAGE`), the first usable byte of a stack slot, with the guard page immediately below — the interrupted stack was fully consumed and the ISR's own prologue crossed it. `#PF` is deliberately not IST-routed (`idt.rs:324`, Linux-faithful), so the guard-page hit escalates straight to `#DF`. | unowned |
