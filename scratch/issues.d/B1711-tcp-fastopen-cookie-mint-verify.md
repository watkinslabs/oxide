# B1711 — TCP fast open: cookie mint/verify and the SYN-with-data handshake

| Status | Sev | Issue | Evidence | Owner |
|---|---|---|---|---|
| OPEN | med | **A SYN that carries FIN alongside its fast-open data is accepted as data-only: the FIN is dropped.** The reference queues the SYN's payload and then runs the ordinary FIN handling on the child, moving it to CLOSE-WAIT with `rcv_nxt` past the FIN. Here the FIN is ignored, so the child stays SYN-RECV owing the peer an acknowledgement it will retransmit the FIN for. Not half-implemented on purpose: `tcp_state::transition` has no `(SynRecv, RecvFin)` arm at all, so the state machine cannot express it and adding one is a change to the ordinary passive path, not to fast open. | `crates/kernel/net/src/tcp_state.rs` has no `(SynRecv, RecvFin)`; `tcp_conn/io.rs` fast-open delivery consumes payload only. A fast open carrying FIN is rare (it needs a client that writes and shuts down in one call). | unclaimed |
| OPEN | med | **`TCP_DEFER_ACCEPT` and passive fast open do not compose.** A fast-open child is published to the accept queue at its SYN, while `defers_segment` still drops the bare acknowledgement that would complete its handshake — so a deferring listener that also fast-opens hands the program a connection whose handshake is then held open by the deferral for the full deferring period. The reference makes the fast-open path bypass the deferral. Not fixed here because the composition needs `defers_segment` to consult the child's fast-open state, which is a change to the defer lane's contract. | `stack/tcp_reqsk.rs defers_segment` does not look at `conn.fastopen_child`. No test asserts the composition either way. | unclaimed |
| OPEN | low | **The reset-penalty list stores expiry deadlines, not the request socks themselves.** The reference parks the whole request for 60 s so it holds a reference; here the request is already unhooked by the ordinary teardown path, so `FastOpenQueue` keeps only `now + RST_PENALTY_NS` per penalty. Observably identical — the overflow check only ever reads the head's deadline, pops it and decrements `qlen` — but a future consumer that wants to *identify* the parked requests will not find them. Deliberate: keeping a second, fast-open-only registry of request socks beside the connection table would be a split source of truth. | `tcp_fastopen/queue.rs Outstanding.penalties: VecDeque<u64>`; pinned by `server_tests::a_reset_connection_a_program_had_taken_keeps_charging_for_a_minute`, which walks the deadline to the nanosecond. | won't fix |

The nearest failure, a full accept backlog, drops the child instead (`publish_fastopen_child`), matching what the ordinary passive path does with a backlog it cannot satisfy. | `stack/tcp_listener_deliver.rs publish_fastopen_child`. ## Curated-ledger rewrites this PR requires

One row in `scratch/known_issues.md` is now wrong and must be REWRITTEN, not flipped:

- The row reading `TCP fast-open codec has no production caller` (and the B1710 drop's
  restatement of it) is **resolved**. `tcp_conn::fastopen::parse` is called from
  `stack::tcp_fastopen::plan` on every SYN a listener receives, and `syn_options` no
  longer hardcodes `fastopen: None` — it carries whatever the decision left. What
  remains true, and is the piece-3 row above: nothing on the **client** side produces a
  fast-open option, so `TCP_FASTOPEN_CONNECT` still opens an ordinary connection.
