# B1739 — cgroup exit state kept in a side table beside the task

| Status | Class | Sev | Issue | Evidence | Owner |
|---|---|---|---|---|---|
| FIXED (this PR) | DEFECT | high | **A task's exit state was recorded in a map keyed by tid, beside the task, where it could disagree with the task itself.** `CGROUP_EXITS: BTreeMap<u32, Weak<Task>>` was consulted by `migrate_hook` to refuse a migration for a task on its way out. The reference has no such table: `cgroup_procs_write_start` tests `PF_EXITING` ON THE TASK. Two records of one fact can disagree, and this one did — an instrumented boot caught the gate refusing PID 1, a task that is plainly neither reaped nor a zombie, so its tid was in the table while it was alive. Replaced with `Task::exiting`, set at the head of both exit paths exactly where the table was written, so the flag is per-Task-object and a recycled tid cannot inherit a stale answer. | Instrumented boot: `[cgprobe] exit-gate ESRCH vpid=1` while `resolve` succeeded, so the refusal came from the table and not from the lookup. Hosted: `the_exiting_flag_lives_on_the_task_and_starts_clear`. The table, its `Weak` values, and the four imports that existed only for it are gone; `cargo build -p sched` is warning-clean. | B1739 |
| OPEN | DEFECT | high | **`make qemu-x86-debug` still fails: PID 1 is still refused its own cgroup, and the cause is NOT the side table.** With the table removed the failure is unchanged — `Failed to create /init.scope control group: No such process` at t≈28.5 s, then `Freezing execution.`, verified on a live `--features debug-all` boot of this branch (log confirmed to be the new kernel: the probe strings are absent). So the ESRCH now comes from one of the other two exits in `migrate_hook`: the vpid resolve returning nothing, or returning a task that is genuinely reaped/zombie, or `cgroup::migrate_process` itself refusing. Note `lookup_by_vpid` falls back to "any group member if the leader has already exited" — a fallback that can hand back a DEAD thread, which the exit gate would then correctly refuse; that is the first thing to check. The earlier instrumented run measured the OLD code and named the table, so it does not narrow the remaining paths. | Live `debug-all` boot on this branch, t=28.5 s, both manager errors present. | unowned |
| OPEN | INFRA | med | **A `debug-all` boot is impractical to iterate on: ~3000 log lines and t≈28 s of guest time in 10 minutes of wall clock.** The serial port is the bottleneck, and the boot has to reach t≈28 s before the defect above appears. Reproducing it needs either a narrower feature set that still perturbs the timing, or a hosted harness that drives `migrate_hook` directly. Chasing it by repeated `debug-all` boots costs ~10 minutes per observation and should not be the loop. | This lane: two `debug-all` boots, one killed at 10 minutes having reached 85 log lines, one reaching t=28.5 s in ~10 minutes. | unowned |
