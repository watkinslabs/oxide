# B1979 — live-gnome desktop segfault

| Status | Class | Sev | Issue | Evidence | Owner |
|---|---|---|---|---|---|
| FIXED (this branch) | DEFECT | High | A file-mapping fault derived its valid extent from the size read BEFORE the fill and judged the fill against that stale value. An object that SHRANK while the fault was in flight — a writer rewriting a file a reader has already mapped, which is what dconf-service does to the databases every GIO client maps — then made the backing's correct "no more bytes" at the new end look like an unrecoverable short read. The fault failed with `Error::Io`, which reaches userspace as a fatal signal: the reader is killed for the writer's truncate. The reference re-reads i_size AFTER the read completes and decides against that; a page still partly inside the file gets an ordinary zero tail, and only a page wholly past the new end faults. Fixed by re-deriving the extent after a no-progress short and only then declaring the fault fatal. | `vmm::tests_shortfill::a_file_that_shrinks_under_the_fault_is_an_eof_tail_not_a_fatal_short`. Positive control: delete the post-read re-check in `fill.rs` and it goes red with exactly `Io`; the other three short-fill tests stay green, so the guard against installing a partially-zero page (B240) is intact. | Chris Watkins |
| OPEN | DEFECT | High | The observed victim was `libdconfsettings.so` +0x5245, `mov (%rax),%edx`, on the pointer `g_mapped_file_new()` returned with its size check already passed — the kernel handed userspace a file mapping and then refused to fault it in. When the victim is `gnome-shell` the desktop dies to a bare console. The row above fixes one mechanism that produces exactly this; whether it is the ONLY one is not established, because a failed fill and an absent mapping are indistinguishable in the log until B1985 lands. Keep open until a live-gnome run has gone long enough without it to be convincing. | `gnome-shell[398]: segfault at 00007f257af04000 ip 00007f257a65b245 ... ino 0x6e54000000003e14 (ext4 inode 15892) off 0x5245`.
