# C274 — zero gateway solicited as a next hop

| Status | Class | Sev | Issue | Evidence | Owner |
|---|---|---|---|---|---|
| FIXED C274 | DEFECT | critical | A route whose `RTA_GATEWAY` is `0.0.0.0` was stored as a gateway rather than as on-link, so `gateway.unwrap_or(dst)` returned the zero. Every transmit to a directly-connected host then solicited `0.0.0.0`, which nothing answers: ARP never resolved, no unicast traffic ever left, and the guest received exactly the 2 broadcast DHCP replies for its whole life. Ping, UDP DNS and TCP DNS all timed out while the interface, address and route table read as healthy and `tx_packets` kept climbing. | guest capture `ARP, Request who-has 0.0.0.0 tell 10.0.2.15`; trace `[ARP-ZERO src=10.0.2.15 ipdst=10.0.2.2 proto=1]` with `[ARP-ROUTE dst=10.0.2.0/24 tbl=254 kind=1 gw=0.0.0.0]`; `crates/kernel/net/src/tests_arp_next_hop.rs` reproduces it hosted | — |
| FIXED C274 | INFRA | med | Nothing could see the wire. Whether the guest sends a frame at all, and whether anything answers, is not decidable from inside it — a driver that never transmits and a peer that never replies look identical. `OXIDE_QEMU_PCAP=<path>` now dumps every frame on `net0`, both arches. | `tools/xtask/src/image_qemu/common.rs` `pcap_filter_args`; the capture is what identified the bad ARP target | — |
| FIXED C274 | COVERAGE | med | No test drove the ARP solicitation path: every transmit test pre-seeded the neighbour cache, so the target address of a request nothing produced was never checked. | `tests_arp_next_hop.rs`; positive control — restoring `gateway.unwrap_or(dst)` fails 3 of its 6 tests | — |
