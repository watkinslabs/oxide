# F786-pkey-arm-enablement

| Status | Sev | Issue | Evidence | Owner |
|---|---|---|---|---|
| OPEN | med | `POR_EL0` is not saved in or restored from the aarch64 signal frame. Upstream defines a `POE_MAGIC` sigcontext record for exactly this, and `records.rs` already declares that magic in its REJECTED list — so a handler that changes its rights keeps the change across `sigreturn`, and a `POE_MAGIC` record supplied by userspace is refused. Symmetric with the x86 lane's XCR0 divergence (F785) and should close with it, in one change that adds the record on both arches rather than one arch at a time. | F786; `hal-aarch64/src/signal/records.rs:64` declares `POE_MAGIC` as unsupported. | — |
| OPEN | low | Only `TCR2_EL1.E0POE` (EL0 overlay) is set, not `TCR2_EL1.POE` (EL1 overlay). This matches upstream — the kernel does not overlay its own accesses — but means `POR_EL1` is untouched and kernel accesses are never subject to a key. Recorded because a future supervisor-key feature would need the other bit. | F786; `por::setup_poe`. | — |
| OPEN | low | `AT_HWCAP2`'s `HWCAP2_POE` bit is not published, so a userspace library probing the auxv for permission-overlay support sees nothing even once the overlay is on. glibc's `pkey_get`/`pkey_set` already emit the raw `POR_EL0` encodings, so they will work; anything gating on the hwcap will not. Closes with the syscall-semantics lane. | F786; no `POE` bit in `isar0_hwcap()`/hwcap publication. | F787 |
| OPEN | med | Same as the x86 lane: this branch enables the hardware and switches the register, but no descriptor carries a Permission Overlay index yet, so nothing userspace does can be denied by a key, and `pkey_alloc` still reports the feature-absent answer. Closes in F787. | F786, by construction. | F787 |
| OPEN | med | Boot smoke NOT taken. Both arches build clean and every decision is hosted-tested, but the `TCR2_EL1`/`CPACR_EL1` writes and the per-switch `POR_EL0` read are exactly what a build cannot prove — and `TCR2_EL1` is a register this kernel has never touched before, on a QEMU CPU model that may not implement FEAT_S1POE at all (in which case `setup_poe` correctly does nothing, which is itself worth confirming). Must boot both arches before merge. | F786; box was under heavy concurrent load throughout the lane. | — |
