# B1658 — `KEYCTL_PKEY_*` / asymmetric keys

| Status | Sev | Issue | Evidence | Owner |
|---|---|---|---|---|
| OPEN | med | `KEYCTL_RESTRICT_KEYRING` still ignores its restriction STRING, so the `asymmetric` type is registered with `restrictable: false` and naming it is ENOENT. Linux accepts `builtin_trusted`, `builtin_and_secondary_trusted` and `key_or_keyring:<id>[:chain]` there, which is how a keyring is made to accept only certificates signed by a key it already holds. Registering the type as restrictable without parsing that string would have been a stub. Fix: teach `restrict_core` the restriction argument (it is not even copied from userspace today), then flip the type. | B1658. `ops/links.rs::restrict_core` takes `ty: Option<&str>` and no restriction; `types.rs` asymmetric row. | — |
| OPEN | low | The asymmetric key type carries no key-ID list, so `KEYCTL_SEARCH` cannot find a certificate by `id:<hex>` / `ex:<hex>` / `s:<hex>` the way Linux's `asymmetric_key_match_preparse` does — only by the exact description. The subject key identifier IS parsed (it is what the proposed description ends with), so the data is present; what is missing is the match-preparse hook and a place on the key to keep the three ids. | B1658. `pkey::x509::Certificate::skid` is parsed and used for the description only. | — |
| OPEN | low | **Deliberate deviation, safety:** `KEYCTL_PKEY_{ENCRYPT,DECRYPT,SIGN}` returns EOVERFLOW when the produced output is longer than the `out_len` the caller declared in `struct keyctl_pkey_params`. Linux instead re-sizes the copy from the KEY (`params.out_len = info.max_*_size`) and then `copy_to_user`s the produced length, so a caller that declares a short `out_len` — which passes the `out_len > max` check — has bytes written past its buffer. Reproducing that would be writing a user-memory overflow on purpose. Callers that size their buffer from `KEYCTL_PKEY_QUERY`, which is the documented flow, see no difference. | B1658, `keyctl/pkey.rs::eds`; the check is `produced.len() > out_len`. | — |
| OPEN | low | RSA private operations do not use the Chinese-remainder representation, so a decrypt/sign costs a full-width `d` exponentiation (roughly 4× the CRT cost). The primes ARE present in the PKCS#8 blob and are parsed past but not retained. Correctness is unaffected; this is throughput on `KEYCTL_PKEY_DECRYPT`/`_SIGN` only. | B1658, `pkey::rsa::parse_private`. | — |
| OPEN | low | Only RSA is implemented. An ECDSA/EdDSA/ML-DSA certificate parses as far as its algorithm identifier and is then ENOPKG, which is the answer Linux gives for an algorithm it was not built with — but it IS absent surface, not a config answer. The `enc=x962`/`p1363` encodings have no meaning here for the same reason. | B1658, `pkey::oid::pkey_algo` maps only `rsaEncryption`. | — |
