# B1736 — `RTM_GETLINK` answered every request with a dump

| Status | Class | Sev | Issue | Evidence | Owner |
|---|---|---|---|---|---|
| FIXED (this PR) | DEFECT | **critical** | **`handle_getlink_in` ignored the request and always replied with a full multipart dump, so a query for ONE device returned whatever was first in the table — loopback.** `RTM_GETLINK` is two requests in the reference. With `NLM_F_DUMP` it walks every device and terminates with `NLMSG_DONE`; WITHOUT it, `rtnl_getlink` resolves the single device the caller named — by `ifi_index`, else by `IFLA_IFNAME` — and replies with one non-multipart `RTM_NEWLINK`, or `-ENODEV`. Ours took only the header, had no access to the request body at all, and answered both forms identically. Every client that queried a device by name or index therefore read **loopback's identity and loopback's flags**. That is why `ip link show eth0` printed `lo`, and why the network manager believed a down, unaddressed `eth0` was already up and externally configured: it asked about eth0 and was told about `lo`, which is `<LOOPBACK,UP>`. | Guest before: `ip -o link show eth0` → `1: lo: <LOOPBACK,UP>`. After: `2: eth0: <BROADCAST,MULTICAST> … state DOWN`, the device actually asked for. Hosted: a by-name single get now returns the named device and asserts the reply is one message, non-multipart, with no `DONE`; plus `ENODEV` for an unknown name, `EINVAL` for a truncated request, and attribute-parsing cases. Positive control: disabling the single-get branch fails the new assertion. | B1736 |
| FIXED (this PR) | DEFECT | **critical** | **The guest now takes a DHCP lease and has working IPv4.** This was the blocker behind "no lease" and behind the `nmcli` oddity reported from the desktop. With the single-device form answered correctly the guest comes up with a full lease and reachable gateway. | Guest after: `2: eth0 inet 10.0.2.15/24 brd 10.0.2.255 scope global eth0`; `ip -4 route` → `10.0.2.0/24 dev eth0 proto kernel scope link src 10.0.2.15` and `default via 10.0.2.2 dev eth0 src 10.0.2.15`; `ping -c2 10.0.2.2` → `1 received, rtt 0.203 ms` (the first packet is lost to ARP resolution). Before: `ip -4 addr` showed only `lo`, no routes, no lease. | B1736 |
| OPEN | DEFECT | med | **The network manager still reports `eth0` as "connected (externally)" even though it now has a lease.** The address, routes and reachability are all correct, so this no longer blocks networking, but the manager's device state is still not derived from the link the way it should be — a device it calls externally-connected is one it will not fully own, which will matter for anything that asks it to reconfigure the link. Worth re-checking now that the single-device query returns real data: the earlier verdict was formed while every by-index query returned loopback, so it may simply be a stale assessment that a fresh probe would clear. | `nmcli -t -f DEVICE,STATE d` → `eth0:connected (externally)` in the same boot that shows the working lease above. | unowned |
