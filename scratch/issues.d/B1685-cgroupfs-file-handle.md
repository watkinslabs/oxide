# B1685 — cgroupfs file handles

| Status | Sev | Issue | Evidence | Owner |
|---|---|---|---|---|
| FIXED B1685 | med | **`name_to_handle_at` on cgroupfs returned EOVERFLOW**, so the service manager could not read any cgroup id (`Failed to get cgroup ID of cgroup /sys/fs/cgroup/system.slice/<unit>, ignoring: Value too large for defined data type` on every unit start). Root cause: the FID codec was VFS-global — one 12-byte `(ino, generation)` payload for every filesystem — while the cgroup-id reader sizes its buffer to `sizeof(uint64_t)` = 8 and does not run the grow-and-retry protocol, so every call overflowed. Fixed by adding the per-superblock encode/decode half of `s_export_op` (the decode half already existed) and giving cgroup2 the kernfs handle: 8 bytes, `FILEID_KERNFS`, payload = the node id, which is the directory's inode number. | B1663 boot log, ~40 occurrences from `system-getty.slice` onward. Now: 9 hosted tests in `cgroup::export::tests` + 4 in `vfs::export::kernfs_fid::tests`. | B1685 |
| OPEN | low | cgroupfs control-file inode numbers pack `(cgid << 8) | slot` into a region 2^27 wide, so the packing wraps for cgroup ids ≥ 2^19 and two cgroups' control files then share inode numbers (and file handles). Directory numbers invert across the full 2^24 region. Pre-existing; pinned by `the_inode_number_derivations_invert`, which asserts both the working range and the wrap. | `cgroup::ids` + `vfs::pseudo_ino::{CGROUP_DIR, CGROUP_FILE}`. | — |
| OPEN | low | sysfs is kernfs-backed in Linux and exports the same 8-byte handle, but oxide's sysfs still reports `export_can_decode_fh() = false` (its inodes are synthesized from live kernel objects with no id→object inverse). `name_to_handle_at` on `/sys` is EOPNOTSUPP where Linux succeeds. Not a live blocker — no observed consumer — but it is the same defect class this branch fixed for cgroup2. | `sysfs::SysfsSuperOps::export_can_decode_fh`. | — |
