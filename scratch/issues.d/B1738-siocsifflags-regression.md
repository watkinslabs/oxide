# B1738 — `SIOCSIFFLAGS` broke when carrier began being reported

| Status | Class | Sev | Issue | Evidence | Owner |
|---|---|---|---|---|---|
| FIXED (this PR) | DEFECT | high | **`SIOCSIFFLAGS` refused every request with EOPNOTSUPP, a regression introduced by B1737.** That lane made `iface_flags` report derived flags (`dev_get_flags`), which is correct — but the ioctl compared that REPORTED word against the caller's `ifr_flags` and rejected any difference outside `IFF_UP`. A caller's `ifr_flags` cannot carry the carrier bits: the field is 16 bits and `IFF_LOWER_UP` is `0x10000`, so the comparison always differed in bits the caller could not have set. The reference does not compare them either — `dev_change_flags` takes only `{DEBUG, NOTRAILERS, NOARP, DYNAMIC, MULTICAST, PORTSEL, AUTOMEDIA}` from the caller and preserves `IFF_UP | IFF_VOLATILE | IFF_PROMISC | IFF_ALLMULTI` from the device. This is the hazard of changing what an accessor MEANS: a comparison site elsewhere changed with it, silently. | Guest before: `ip link set eth0 up` via the ioctl path failed. After: `rc=0`, and the link toggles cleanly — `ip monitor link` shows `<BROADCAST,MULTICAST> state DOWN` then `<BROADCAST,MULTICAST,UP,LOWER_UP> state UP`. Hosted: four tests, and the decision moved OUT of the target-gated slot file into `iff::siocsifflags_supported` so `cargo test` actually compiles it — a test left in `siocgif.rs` would never have run. Positive control: restoring the old comparison fails two of them. | B1738 |
| OPEN | DEFECT | high | **Name resolution still fails, and the kernel side is now proven correct.** The resolver has everything it needs — `DNS Servers: 10.0.2.3`, `Default Route: yes`, `/etc/resolv.conf` → `127.0.0.53`, stub listeners bound (`127.0.0.53%lo:53`), service active — and still reports `Current Scopes: none` and `Total Transactions: 0`, i.e. it never attempts an upstream query. A query over D-Bus, which bypasses the stub socket entirely, fails identically (`No appropriate name servers or networks for name found`), so the stub path is NOT implicated. What the kernel presents was checked against what the resolver requires for a link to be usable, and all of it is correct: `IFF_UP | IFF_LOWER_UP` both set, operstate `IF_OPER_UP` (6, matching the reference's enum), a global-scope address, and working multicast notifications — `ip monitor` receives both `RTM_NEWADDR` on address add and `RTM_NEWLINK` on each link transition, carrying the right flags. A static trace of the whole `127.0.0.53:53` UDP path (route lookup over the `127.0.0.0/8` local route, local-delivery admission by `is_loopback`, exact-address UDP demux, loopback device passthrough, source-address selection, checksum, wake) found no defect either. So the remaining cause is in the resolver's own link-relevance state machine, not in what the kernel reports to it. | All of the above measured on one live boot of this branch. | unowned |
