# B1735 — ethernet NICs were registered administratively UP

| Status | Class | Sev | Issue | Evidence | Owner |
|---|---|---|---|---|---|
| FIXED (this PR) | DEFECT | high | **Every non-loopback netdev was registered with `IFF_UP | IFF_RUNNING` hardcoded, before userspace had ever touched the link.** The reference registers an ethernet device administratively DOWN — `ether_setup` sets `dev->flags = IFF_BROADCAST|IFF_MULTICAST` and nothing more — and `IFF_UP` arrives only when userspace asks, via `ip link set up` / `SIOCSIFFLAGS` / `RTM_NEWLINK`. Loopback is the reference's exception: it is registered and then opened during its own namespace init, so it is always up, and that end state is stamped here directly. Registration state now matches the reference exactly. | Guest before: `eth0` appears UP in the very first link dump. After: `2: eth0: <BROADCAST,MULTICAST> mtu 1500 state DOWN`, with `lo` still `<LOOPBACK,UP>`. Hosted: `an_ethernet_nic_is_registered_down` and `loopback_is_registered_up`. | B1735 |
| FIXED (this PR) | COVERAGE | med | **Two AF_PACKET transmit fixtures depended on registration implying UP.** `packet_ring_tx_tests::fixture` and `packet_policy_tx_tests`'s fixture registered a device and immediately expected it to carry frames. The transmit path refuses a down link (`sock/packet_tx.rs` gates on `IFF_UP`, which is the reference's ENETDOWN), so with registration corrected one test HUNG — it waited on a barrier the device could only reach if transmit called into it — and five more failed. Both fixtures now bring the link up the way userspace would, so they model the real sequence: register down, bring up, then transmit. A fixture that skipped the bring-up was quietly asserting a non-Linux link lifecycle. | `cargo test -p net` 1951 passed / 0 failed. Before the fixture fix: one test running >60 s, five FAILED. | B1735 |
| OPEN | DEFECT | high | **The network manager still marks `eth0` "connected (externally)" and never activates it, so the guest takes no DHCP lease.** Correcting the registration flags was necessary but NOT sufficient. With the link now genuinely DOWN and carrying no addresses, the manager still reports `GENERAL.STATE:100 (connected (externally))`, `GENERAL.REASON:0 (No reason given)`, `NM-MANAGED:yes` — a device it believes is connected while the kernel reports it down and unaddressed. That contradiction says the verdict is not being drawn from the current link state, so the remaining cause is on the manager's side of the interface: either it is not receiving the `RTM_NEWLINK` state notifications that would correct it, or its initial assessment is made from something other than the link dump. Next step is the manager's own log (`journalctl -u NetworkManager`), which has not been read yet — every probe so far has queried state, not the reasoning behind it. | Guest, after this fix: `ip -o link` shows `eth0 … state DOWN`, `/sys/class/net` lists `eth0`, `ip -4 addr` shows only `lo`, and nmcli reports the state above. | unowned |
| OPEN | INFRA | med | **`tools/boot-smoke-dhcp.sh` cannot pass regardless of DHCP correctness — it greps for a marker from the retired userspace.** It waits for `udhcpc: configured eth0` and the Makefile sets `OXIDE_UDHCPC_ENABLE=1` for a busybox `rcS` gate. That pipeline belongs to the musl/busybox rootfs that the glibc staging replaced; the shipped Fedora image has no `/sbin/udhcpc`, no `/etc/init.d/rcS`, and nothing reads `OXIDE_UDHCPC_ENABLE` anywhere in the tree. So its `FAIL — timeout without lease` is not evidence about DHCP either way. It needs to check for a lease the way the current image would show one (an address on `eth0`, or the manager's own log), or be deleted. | `boot-smoke-dhcp.sh` marker vs `debugfs -R stat` on the shipped image: all three paths "File not found". | unowned |
