# B1729 — every cgroup-id read failed, and it was the only failure in the boot

| Status | Class | Sev | Issue | Evidence | Owner |
|---|---|---|---|---|---|
| FIXED (this PR) | DEFECT | high | **`name_to_handle_at` took the export ops from the INODE's superblock back-pointer, which every pseudo-filesystem leaves unset, so cgroupfs's own 8-byte handle encoder was never consulted and the service manager got EOVERFLOW for every cgroup.** The reference reaches these ops through the dentry (`dentry->d_sb`), which is always populated because an inode cannot exist without a superblock. Here `i_sb` is a `Weak` the inode builder must be TOLD to fill, and only ext4 and devnode fill it — every filesystem that synthesizes inodes on lookup (cgroupfs, procfs, sysfs) leaves it empty. So the width fell back to the VFS-generic 12-byte `(ino, generation)` FID for exactly the filesystems that override it. The cgroup-id reader sets `handle_bytes` to `sizeof(uint64_t)` and does not run the grow-and-retry protocol, so it failed every time. cgroupfs's `CgroupSuperOps` was correct, complete, wired at `fs.rs:38`, unit-tested, and unreachable — the machinery-without-callers class, one indirection further out than usual. Both `name_to_handle_at` and `open_by_handle_at` now take the superblock from the path's mount, falling back to the inode's. | **25 → 0.** A clean release build of `main` produced 25 `Failed to get cgroup ID of cgroup …: Value too large for defined data type` in one boot — one per cgroup, and the ONLY failure of any kind in the log (no failed services, no failed mounts, no dependency failures; `grep -oiE "Failed to [a-z ]+"` returns that one message and nothing else). After the fix, zero on both arches, and zero `Failed to` of any kind. `boot-smoke` PASS x86 76 s, arm 62 s. Hosted: `crates/kernel/vfs/tests/export_sb_source.rs`, 4 tests, with a positive control — reversing the preference to `inode_sb.or(mount_sb)` fails `the_mounts_superblock_is_preferred_over_the_inodes`. | B1729 |
