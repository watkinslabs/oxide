| OPEN | DEFECT | high | **The hardirq stack overflows because the RX/softirq chain spends ~3.2 KiB in three frames, on a stack with ~1.5 KiB of headroom.** Measured from `objdump -d` of the release kernel (`sub $N,%rsp` per function), restricted to functions reachable from the IRQ dispatcher and the softirq drain. Top of the ranking: `net::stack::tcp_listener_deliver::build_passive_child` **1816 B**, `kmain::hooks::tick_poll_combined` 1096 B, `modules::linux_irq::linux_irq_dispatch` 1032 B, `net::stack_ipv6::control::ipv6_control_tick` 952 B, `net::stack::ipv4::deliver_rx_in` 888 B, `net::arp_timer` 888 B, `drv_virtio_input::drain::queue::drain_softirq` 808 B, `net::raw4::rx::deliver_raw4` 776 B. One live chain — `deliver_rx_in` → `deliver_tcp_to_listener` (520 B) → `build_passive_child` (1816 B) — is 3.2 KiB before anything else on the stack, which is why an arriving UART RX interrupt is the last straw. `build_passive_child` is the single biggest and the obvious first target: a passive TCP open builds its child by value on the softirq stack; boxing it (or building it in place) removes ~1.8 KiB from the deepest path. Linux keeps these paths shallow for the same reason — `THREAD_SIZE`/`IRQ_STACK_SIZE` is 16 KiB there too, and a 1.8 KiB frame in `tcp_conn_request` would be treated as a bug. | Command recorded so the ranking is reproducible: `objdump -d --no-show-raw-insn <kernel.elf>` + per-function `sub $imm,%rsp` extraction, filtered to the IRQ/softirq path. Full build: `cargo run -p xtask -- kernel --arch x86_64`. | unowned |
