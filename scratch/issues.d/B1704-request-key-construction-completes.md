# B1704 — request_key construction completes

| Status | Sev | Issue | Evidence | Owner |
|---|---|---|---|---|
| FIXED B1704 | high | **The `request_key(2)` construction never completed on a booted system** because the assumed instantiation token did not survive the helper's own credential transitions. `/sbin/request-key` assumes authority over the key, EXECS the handler its configuration names, and that handler FORKS `keyctl instantiate` to answer. The exec hook DROPPED the token and the fork hook never COPIED it, so the program that finally answers held no authority and `instantiate_core` returned EPERM — the helper exited non-zero and the key was left under construction, then negated. Neither hook is what the reference does: `prepare_exec_creds` touches only the thread and process keyrings, and `prepare_creds` takes a reference to the same token for the child. | `keyring/lifecycle.rs` `fork`/`exec`; four positive controls, each reinstating one defect, go RED. | this lane |
| FIXED B1704 | med | A helper had no reach into the REQUESTER's keyrings: only `search_cred_keyrings_rcu` existed, never `search_process_keyrings_rcu`, so a handler needing one of the requesting task's keys found nothing. Added `ops::search::search_process` — own keyrings, then the requester's under the requester's credentials while a live token is held, with the outcomes merged by the same `success > -ENOKEY > -EAGAIN > other` priority. A TOKEN is deliberately not reachable that way. | `keyring/ops/search.rs`; `chain::the_requester_reach_is_token_scoped_and_never_yields_a_token`, controls with the guard forced open and the fallback forced closed both go RED. | this lane |
| FIXED B1704 | high | The `debug-umh` boot self-test's two `absent-*` cases used `/sbin/request-key` as the guaranteed-missing program. Shipping keyutils in the images made that path EXIST, so both cases silently started reporting success — a self-test passing by testing nothing. Now a path nothing can install. | `umh/src/spawn/selftest.rs` `ABSENT`. | this lane |
| FIXED B1704 | high | No coverage of a helper that submits a SECOND helper request while the first still runs (the pool-growth deadlock case) on a booted system. The probe now runs a second construction whose handler asks the kernel for another key before answering, via a rule injected into the package's own drop-in directory. The outer payload carries the inner key's serial, so the outer construction cannot pass unless the inner one completed while it was still in flight. | `tools/xtask/src/rootfs_disks/request_key.rs`, `userspace/probes/request_key`. | this lane |
