| FIXED B1704 | high | **The `request_key(2)` construction never completed on a booted system** because the assumed instantiation token did not survive the helper's own credential transitions. `/sbin/request-key` assumes authority over the key, EXECS the handler its configuration names, and that handler FORKS `keyctl instantiate` to answer. The exec hook DROPPED the token and the fork hook never COPIED it, so the program that finally answers held no authority and `instantiate_core` returned EPERM — the helper exited non-zero and the key was left under construction, then negated. Neither hook is what the reference does: `prepare_exec_creds` touches only the thread and process keyrings, and `prepare_creds` takes a reference to the same token for the child. | `keyring/lifecycle.rs` `fork`/`exec`; four positive controls, each reinstating one defect, go RED. | this lane |
| FIXED B1704 | high | Second half of the same failure, and the one the exec/fork fix exposed: with the token finally reaching `keyctl instantiate`, the answer had nowhere to go — the destination the stock handler names is `%S`, the requester's session keyring, which grants its owner View and Read through the user byte and Write only through the possessor byte. Possession was computed from the CALLER's keyrings only, so the helper was denied and the construction ended EACCES -> negate -> ENOKEY. `lookup_user_key` decides possession by searching the process keyrings, which follows the token into the requesting task's keyrings.
