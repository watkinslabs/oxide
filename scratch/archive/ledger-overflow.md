## KI-0309

B2679, reverted. Turnstile wait was measured at 1.84 ms against 0.40 ms of device time once the B2677 write flood was gone, so this is the boot's dominant remaining cost and the payoff for fixing the owned path is large. First attempt also panicked in `RunqueueInner::enqueue: idle` because the wait slept unconditionally — the idle task reads blocks; a `can_sleep` guard fixed that and is worth keeping in any retry. **B2680 narrowed it by reading, and four theories are now dead:** descriptor ownership is correct (heads are strided by `MAX_REQUEST_DESCRIPTORS`, so a request owns `head..head+3` exclusively); the synchronous and owned paths DO exclude each other (`post_owned_request_inner` defers while `ring.busy`, `drain_admitted` refuses to drain while `busy`, and `acquire_turn` waits for `pending` and `deferred` to empty, so a used entry is never claimed by the wrong observer); the interrupting queue IS drained, by `run_completion_bottom_half` in the block softirq; and the head pool is large enough (`size/3`, ~85 for a one-frame queue), so deferral is not the common path. What remains, and it is written in the engine itself: `run_completion_bottom_half`'s doc says *"The current request engine has one owner at a time... Keeping the IRQ side to a bit raise is required before the engine can safely grow to multiple outstanding descriptor chains."* The experiment confirmed the code's own warning. The next lane should start at what makes a second outstanding chain unsafe — the deferral path (`start_deferred_requests`, which runs inside the drain loop and re-posts with the caller's retained completion) is the least-exercised piece and the first place to look. **B2682 RETRACTS the corruption claim.** A completion cross-check (`debug-blk-verify`) compares every used-ring entry's `len` against what the request should have moved. Re-running the failing experiment with it armed: **zero mismatches, and the SIGBUS still reproduced.** The device completed every chain it was given, for the chain it was given, with the right byte count. So "a read returning the wrong bytes" was an inference from the symptom, not a measurement — a bus error on a mapped page is equally what a read that FAILS looks like, and the same boot showed `udev ... taking a long time`, `Connection refused`, and no completion within the helper's 5 s timeout. The live hypothesis is now a completion STALL — a request whose completion is not delivered promptly, timing out into `Eio`, which ext4 turns into a failed page fill and the fault path into SIGBUS. Look at what raises and drains the block softirq when several chains are outstanding, not at data paths. **B2684 retracts the stall hypothesis too, and corrects the shape of the failure.** Per-chain latency and completion-status detectors, run against the same experiment: **zero error statuses, zero length mismatches, completions overwhelmingly under 1 ms (deepest bucket 100 ms, none at or above 1 s), deepest in-flight 5, 47-133 deferrals.** Completions are prompt AND correct, so it is not a stall and not wrong data on any run that was measured. **The failure is INTERMITTENT and was being characterised from single boots** — the repository's own lesson about this, ignored. Across five experiment boots the bus-error count was 1, 7, 8, 1 and 0; the clean run also reported 2000 filesystem reads through the helper with 0 errors and 0 timeouts. So a boot can carry the change with no visible fault at all. What the next lane needs first is a RATE, not another single boot: run the experiment ten times, record bus errors per boot with the detectors armed, and only then look for a mechanism that fires in roughly four runs out of five. Two hypotheses have now been retracted by measurement here (corruption, then stall); a third guess is worth less than the rate. **B2685 measured the rate and three more facts.** Ten experiment boots: bus errors 1, 7, 8, 1, 0, 5, 0, 18, 9, 13 — **eight of ten boots affected**, so any single-boot verdict about this is worthless. With every failed read reported (the earlier counter only printed on successes and could never have shown one): **zero failed reads and zero timeouts on a boot carrying eight bus errors.** Every read returned success, with a completion already verified for status, length and latency. So the fault is not in the data path. What the experiment actually changes is CONTEXT: `wait_for_completion` on the compatibility path polls the used index first and returns without sleeping whenever the device is already done, while the experiment's helper always posts and parks. It makes the page-fault path sleep far more often than it used to. The next hypothesis to test is therefore whether the fault path is safe to sleep in at that point — a fault that parks while holding VMA or mapping state, or a retry that mis-handles a fill that slept — rather than anything about the owned-request engine, which has now checked out under every measurement applied to it. **B2687 re-ran the rate with the `in_atomic` fix (B2686) in place: it does NOT fix this.** Six boots gave bus errors 0, 4, 0, 0, 1, 1 against 1, 7, 8, 1, 0, 5, 0, 18, 9, 13 before — fewer, but the sample is far too small to call that a reduction, and the boot still fails: only ONE of six reached `GNOME Shell started` inside 95 s where the baseline reaches it at 21 s, and one run shows `debug-shell.service: Failed with result 'core-dump'` with the restart counter at 8. **Processes are crashing, so wrong pages do reach userspace** — even though every read returns success with a completion verified for status, length and latency. That combination points at a RACE the sleeping path exposes rather than at any single request. `Ext4FrameStore::begin_fill` is only an eviction gate, not a per-page fill lock, and the design accepts concurrent fills: 'a concurrent filler that won the publish race frees the loser's frame'. But `fill_window` fills a SIXTEEN-page readahead window, so two faults on nearby pages fill heavily overlapping windows. Behind the one-request turnstile those fills serialise and never overlap; on the owned path they overlap constantly, and a losing frame that some fault already mapped would be freed while mapped — the free-while-mapped class this tree has hit before. **B2688 killed that hypothesis and three more, then found the one the code already documents.** The publish-race loser frees a frame it allocated privately and never published, so no fault can have mapped it — that path is safe. Running the experiment against the detectors this tree already has: `debug-fillverify` reports **zero `[FILLRACE]` and zero `[FRAME-CORRUPT]`** across three boots carrying 1, 5 and 5 bus errors, so the block layer returns consistent bytes and the cached frame is not written after fill; `debug-fwm` reports **zero** free-while-mapped. Seven mechanisms tested, seven clean — the data is correct at every layer that can be measured. **The leading hypothesis is now the one `mm-vmm/src/address_space/fault/file.rs:161` warns about in its own comment:** *"size_hint (vfs i_size) and the backing's own clamp (on-disk inode size) can desynchronize — a too-small size_hint made `valid == 0` skip the fill AND the short-guard, silently installing a zero page over real file content."* A zero page installed over library text explains every observation together: every data-path detector clean (the read, the cache and the frame are all correct — the fault handler never used them), processes core-dumping, SIGBUS at an address inside a mapped library, intermittent, and appearing only once the path sleeps, which widens the window in which `size_hint` is stale. **B2689 ran that instrumentation and it refines the target again.** Three boots with `debug-atexit` armed: a clean boot logged 93 `[FILLTAIL]`s, all legitimate EOF-straddling last pages; a boot with 5 bus errors logged 408 `[FILLTAIL]`s and — the correlation — **one `[MAPZERO]`**, the marker this tree's own comment predicts for a zero page installed over real content. But two things rule the simple version out: **no fill had `valid=0`** in any run, and **`[SIZE-DESYNC]` never fired**, so the too-small-`size_hint` path was never taken. The `[MAPZERO]` line reports `want` and `got` both all-zero at offset 0xb40 of ino 6e54000000004061 — the mapped page and the backing agree, and both are zero. The bus errors themselves also read differently than assumed: error code **4**, a user-mode READ of a non-present page, with the fault address NOT equal to `ip` (`bus error at 0x7f0229173ac2 ip 0x7f0229ce7e9d in libc.so.6`). That is a data read into a mapping, not execution of a corrupted text page — which is what SIGBUS means for an access past a mapping's EOF bound. **B2690 found the mechanism.** SIGBUS on a user fault has exactly two sources: a poison marker (`user_as/uffd.rs`, whose only production writer is `UFFDIO_POISON` — a new always-on `[POISON-SIGBUS]` log proves it never fires on these boots) and `FaultFailure::BusError`, which `fault_signal.rs` produces from `Error::Io`/`Error::Fault` — **a fill that could not supply the page**. Running the experiment with `debug-shortfill`: **18 bus errors alongside 37 `[SHORT-FILE-FAULT-FATAL]`, and 17 alongside 24** on a second boot. The log lines name it: `off=0x150000 valid=0x1000 size=0x161c30`. `valid` is a FULL page and the offset is far inside the file, so this is not an EOF case — `backing.read_at` returned SHORT for a mid-file page, `filled < valid` made the fill fatal, and the process died. The fault computes `valid` from the inode's `i_size` while the backing clamps its read to the `Ext4FrameStore`'s own `size`; when the store's size lags the inode's, every page between the two reads short. That is the desync `file.rs:161` warns about, in the OPPOSITE direction from the one the `desync` guard recovers (it handles the hint being too SMALL). The reference uses ONE `i_size` for both the SIGBUS bound and the read clamp, which is the shape of the fix: give the bound and the clamp a single source rather than letting a fault trust one size and the backing another. Not attempted here — the guard exists to stop a partially-zero page being installed silently, which is real corruption, so changing it needs its own lane with the short-fill tests as the gate. The fatal log is now always-on: a process dying deserves the four values that diagnose it.
