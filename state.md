## Current blocker — analysis (next session starts here)
Symptom: `Unexpected error response on installing NameOwnerChanged signal match: Connection terminated` — logged 75×/boot. systemd (PID1) connects to the system bus and calls `AddMatch` for `NameOwnerChanged` (org.freedesktop.DBus) to learn when a Type=dbus service acquires its `BusName=`. The response is "Connection terminated" — **the socket to dbus-broker drops on that request.** Consequence: systemd never sees a service acquire its name → every Type=dbus unit (upower `org.freedesktop.UPower`, udisks2, switcheroo, polkit, NetworkManager…) is reported `Failed with result 'timeout'` after its ~90s start timeout, and its Restart= loop re-runs it. multi-user.target waits on those jobs → graphical.target queued, never reached. (upower now gets PAST user setup — it exits 265/271 on the SIGTERM systemd sends at the timeout, not a real crash.)
**Investigated this turn (narrowed, not yet fixed):**
- The AddMatch message is SENT INTACT: `init` (PID1) `writev`s a 92-byte message containing the contiguous ASCII `NameOwnerChanged` to **fd 3** (the bus socket), exactly **45× = 1:1** with the 45 "Connection terminated". So the match rule is not corrupted/truncated at the send side.
- It is NOT a `recvmsg` EOF on the connection: a trace of `sys_recvmsg` returning `<=0` for `name=="init"` on a `SockKind::Unix` stream fired **0×**. So systemd does not learn of the termination via a 0-byte recvmsg on a Unix-stream socket.
- dbus-broker is STABLE (started once, `[EXIT]`=0, no restarts) — it is closing individual client connections, not crashing.
- dbus-broker logs to the journal, NOT stderr (fd 2), so the `[EW ...]` stderr trace does not surface its disconnect reason.
**Next (unresolved):** determine the termination MECHANISM. The `writev` of the AddMatch may itself return EPIPE (dbus-broker already closed the connection BEFORE this message — so the real close is on the PRIOR message/op), or systemd sees POLLHUP via poll/ppoll, or the bus connection is a SockKind OTHER than `Unix` (check what `connect()` to a listening AF_UNIX path yields — accept()'d kind). Steps: (1) log the `writev` RETURN for the 92-byte NameOwnerChanged message (EPIPE? short? ok?); (2) trace `close`/`shutdown` on fd 3 and which task does it; (3) identify fd 3's `SockKind` for PID1; (4) trace the message IMMEDIATELY BEFORE on that fd (the AddMatch may be fine and a PRIOR op triggers the close). Then cross-ref dbus-broker `repos/bus1/dbus-broker` driver AddMatch / connection-teardown (it closes on protocol violations, oversized/over-limit, or bad message framing) and systemd `sd-bus` `bus_add_match`. Note: `writev` writes each iovec via a SEPARATE `file.write()` (crates/kernel/syscalls/src/020_writev.rs loop) — verify that a multi-iovec D-Bus message (header iovec + body iovec) concatenates correctly on the stream and dbus-broker's framing isn't confused (unlikely on an unbounded VecDeque ring, but confirm).
